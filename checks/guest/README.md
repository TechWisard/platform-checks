# One disposable Windows 11 evaluation guest

This directory is a standalone API test fixture. It installs one Windows 11 Enterprise LTSC 2024 Evaluation x64 guest on a disposable Ubuntu 24.04 GitHub runner, then runs the existing session contract experiment inside its actual console session. The guest supervisor, host orchestrator, workflow, media facts, and environment guard are reviewable source.

**Current status: actual Windows 11 x64 installation, the owned elevated A console, Secure Boot and TPM 2.0 were observed again in [run 40708330637](https://github.com/TechWisard/platform-checks/actions/runs/40708330637), job `122886408707`. Its activation prerequisite failed normally.** Eleven completed, successfully parsed primary-license queries each observed exactly one candidate, `LicenseStatus=5` and `LicenseStatusReason=3221549065` (`0xC004F009`). The final bound result was `activation_not_observed`, not the activation watchdog or host deadline. QMP continued to report running; the owned power requests and host resources were cleaned up. The guest never compiled or ran the child-session/frame/input harness in that run.

Microsoft documents status 5 as Notification and `0xC004F009` as expired activation grace. These do not by themselves establish that the 90-day Evaluation period expired. The earlier [run 40696191837](https://github.com/TechWisard/platform-checks/actions/runs/40696191837) ended in unexplained silence; this newer observation must not be assigned retrospectively as its cause.

This source revision adds read-only evaluation/time observations and at most one ordinary `SoftwareLicensingProduct.Activate()` request on the same installed primary product, followed by fresh licensing queries. **It has not yet executed in Windows.** Local Python, managed and PowerShell synthetic tests are contracts, not actual provider or guest evidence. The fixture does not verify physical input isolation or a complete native multiseat implementation; both result flags remain `false`.

## Integration and invocation

The existing independent harness must remain at `checks/session/child`. Copy this directory and the supplied `.github/workflows/windows-guest.yml` into the same test repository. Apply only the narrow guard extension and copy its shared helper:

```sh
git apply checks/guest/guest-environment.patch
cp checks/guest/DisposableGuestReceipt.cs checks/session/child/DisposableGuestReceipt.cs
```

The patch preserves the existing Windows GitHub runner guard and adds a separate, explicit owned-guest receipt. It does not pretend the guest is a hosted Windows runner. The receipt checks the actual SMBIOS UUID, current non-SYSTEM identity digest, current console session, expiry, and observed Secure Boot/TPM facts. This is protection against accidental execution in the wrong environment, **not a cryptographic attestation or a security boundary against a local administrator**. The payload builder requires the harness copy of the helper to match this copy exactly.

The workflow has two explicit invocation paths. `workflow_dispatch` defaults to `validate-only`, which validates local source without acquiring or executing Windows; choosing `execute` runs one guest. Alternatively, a push to `main` that changes exactly the designated trigger path `checks/guest/run-request.json` requests execution. Publish the complete reviewed source first, then create that small request file in a separate final commit, using `run-request.example.json`'s schema and a fresh descriptive request ID. The example filename does not trigger execution. Changing any other guest source file alone does not trigger this workflow. The selected trigger uses the existing concrete evaluation scope; there is no extra approval boolean or fabricated prerequisites checkbox. Do not submit a second run request while the first is active; concurrency cancellation is disabled to preserve owned-VM cleanup.

```sh
python3 -m unittest discover -s checks/guest -p 'test_*.py' -v
cd checks/guest
dotnet build GuestSupervisor/GuestSupervisor.csproj \
  --configuration Release --output build --configfile NuGet.Config --nologo \
  -p:UseSharedCompilation=false -p:NuGetAudit=false -nodeReuse:false
cd ../..
python3 checks/guest/run_guest.py
```

Only the workflow's execute step invokes `run_guest.py --execute` under `sudo`. It preserves only the four named runner environment variables; it passes no GitHub token into the guest. There is no artifact upload, media cache, screenshot publication, remote desktop listener, VNC listener, public monitor, or forwarded port. The failure-only image classifier described below deletes its private temporary input.

The additional pure managed contract checks can run on Linux without calling Windows APIs:

```sh
dotnet build ContractTests/ContractTests.csproj --configuration Release \
  --configfile NuGet.Config --nologo -p:UseSharedCompilation=false -p:NuGetAudit=false -nodeReuse:false
dotnet ContractTests/bin/Release/net8.0/ContractTests.dll
```

## Fixed media, applicable terms, and acquisition

The exact applicable file was extracted from index 1 at:

```text
/Windows/System32/en-US/Licenses/Eval/EnterpriseSEval/license.rtf
128342 bytes
SHA256 6b5d4b32236a921bacdefe19852ec0699ca2eacd72d4e57f50a2de06ede21c8e
```

The complete April 2024 terms were read before preparing execution. Section 14.d includes restrictions for limited versions; section 14.d(ii) permits evaluation, testing and demonstration within the evaluation period and excludes live operation. Section 2 contains instance, user and virtualization restrictions. The reviewed scope is one disposable guest for synthetic, single-operator API evaluation, without production, revenue service, distribution of Windows, remote human seats, or a claim to additional Windows user rights. The full applicable terms continue to govern; this test fixture does not grant a license or determine entitlement to deploy a product.

Every execution extracts the selected WIM metadata and that exact license again from its freshly downloaded ISO and compares them to the fixed facts. A changed destination, size, edition or license stops the run before accepting setup. The full ISO is acquired only during execution. No independently published Microsoft whole-ISO digest was located for this exact LTSC image. Its computed SHA256 is reported with `microsoft_published_digest_compared=false`; an ETag or a community digest is not presented as Microsoft's SHA256. HTTPS acquisition, the exact version/size check, and exact license comparison do not equal an independent whole-image signature verification.

`sdk-source.json` pins Microsoft's Windows x64 .NET SDK **8.0.427** zip and the SHA512 from [official .NET 8 release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/8.0/releases.json). The archive must contain the 8.0.427 SDK and Windows Desktop runtime/reference pack 8.0.33. A local `global.json` disables SDK version roll-forward both for the workflow's supervisor build and the guest's offline build, even when other SDKs are installed on the runner. The guest receives the SDK on a read-only payload CD and compiles the harness with all NuGet sources cleared. It does not download dependencies inside Windows.

Microsoft's [Evaluation Center](https://www.microsoft.com/en-us/evalcenter/evaluate-windows-11-enterprise) describes registration/account and evaluation requirements. This fixture submits no registration form and invents no personal information. If ordinary supported unattended installation still requires an interactive account, registration, license, or other mandatory setup step, it does not bypass that step; failure to reach the supervisor remains a setup/first-logon timeout. A timeout alone cannot identify the unseen exact setup page. An optional fixed-label failure observation is diagnostic only and does not satisfy an outstanding setup requirement.

## Installation and guest boundaries

The host first measures CPU, available memory, free disk, `/dev/kvm`, KVM API 12, and successful creation/closure of an owned empty KVM VM object. It requires four CPUs, at least 11 GiB available memory and 80 GiB free space before installation. These are measurements on that runner, not assumptions based on a runner label. Official Ubuntu packages provide QEMU, OVMF, swtpm, xorriso, wimlib and Tesseract with English data; no PPA or trust-store modification is added.

The VM has four vCPUs, 8 GiB RAM and one owned 64 GiB sparse qcow2 disk, plus read-only installation/setup/payload CDs. It uses `q35`, SMM, Microsoft-enrolled OVMF variables, TPM 2.0 CRB backed by its own swtpm state, and **only KVM** acceleration. It is initially paused; QMP must report KVM present and enabled before the first boot. There is no TCG fallback. Ordinary e1000e user-mode NAT is available for normal Windows activation, with no `hostfwd` entry or public port.

The standard answer file selects only image index 1 and its single owned disk. It specifies locales in both `windowsPE` and `oobeSystem`, creates a unique fresh local administrator A with a random strong password, and requests one initial AutoLogon. It uses one short FirstLogonCommands entry, because these commands run before the desktop and multiple entries can execute concurrently. That entry starts the ordinary own-A supervisor and returns immediately. The supervisor verifies its actual elevated non-SYSTEM A token; it does not prompt for elevation or obtain a privileged token from another process.

The normal Windows Setup `specialize` pass also writes exactly two documented presentation policy values on this new fixture: `EnableFirstLogonAnimation=0` and `DisablePrivacyExperience=1`. They apply before A's and B's first sign-ins. The supervisor reads the exact DWORD values back and reports them. These settings concern the first-sign-in animation and privacy experience. Their presence does not identify any particular past dialog, prove that a window is visible, bypass account registration, or replace the real frame/input checks. Setup runs its own specialize commands in the documented system context; the session experiment subsequently runs as the created non-SYSTEM account A.

### Setup credentials are removed before B exists

The password-bearing answer file is confined to a small separate **SESSIONSETUP** CD in the host's private temporary directory. **SESSIONPAYLOAD** contains no answer file or password; it carries only SDK/source/binaries and nonsecret per-run configuration.

After validating its SMBIOS UUID and A identity, the supervisor disables AutoLogon and deletes the owned Winlogon password value without reading it. It proves the single SESSIONSETUP CD was readable, closes that file immediately, then sends one bounded serial phase. The host pauses only its owned VM, opens `setupcd`'s tray without forcing a drive lock, removes the medium, verifies its `answerbackend` has no `inserted` medium, deletes its setup ISO, and resumes the VM. It does not change the payload or installation CD. Any failure leads to disposal of the owned VM, including when paused.

The supervisor independently waits up to 60 seconds for the same CD drive to be not ready and its formerly readable answer file to fail with a specific missing-file/path or not-ready error on three observations. Access denied or an unknown error does not prove removal. B creation and the harness cannot begin before this observation. The host's own detached-medium proof is also mandatory for success. Passwords, answer XML, accounts, SID strings, tokens, UUIDs and binding nonces are excluded from public logs.

After interactive desktop readiness, `OwnedAnswerFiles` checks only the six fixed Unattend/Autounattend candidates in the documented Panther cache locations. It accepts absence only on native errors 2/3. For an existing file, it uses a bounded XML reader with DTDs prohibited, skips Password subtrees, and requires the exact per-run owner marker in Description. It then marks that same verified, non-reparse file handle for deletion; it does not close a verified handle and later delete a potentially replaced path. An unknown file, denied access, active writer, invalid XML or missing owner marker stops the test. A fresh absence check occurs again immediately before the harness can create B. No directory traversal, registry answer-file pointer following, arbitrary-file deletion or password-value interpretation is performed. These checks concern the known setup cache candidates, not a forensic claim that all Windows traces have been erased.

## Actual evidence required

After verifying its owned elevated A identity, the supervisor creates one `PowerCreateRequest` object and sets `SystemRequired` and `DisplayRequired`. Both calls must succeed. These temporary requests keep an idle GUI test awake; they do not change power plans, registry settings or user-initiated sleep. The common cleanup independently clears both successful requests and closes the owned handle, reporting each numeric API status. Acquisition and verified release are mandatory for a passing result. This is a fixture prerequisite, not a diagnosis of the earlier stall.

After setup media removal, the supervisor requires its process session to be the active console, WTSActive, on the input desktop, with a shell window in the same session for ten consecutive observations. It checks actual Secure Boot with `Confirm-SecureBootUEFI` and actual ready/enabled/activated TPM 2.0 through the documented TPM interfaces. It observes normal activation through `SoftwareLicensingProduct`, selecting the licensing status/reason, remaining grace minutes, evaluation end date, trusted time and product ID under provider-side predicates for the Windows ApplicationID, installed partial key and `LicenseIsAddon=FALSE`. The key remains a presence predicate only; no key value, product name, installation ID or licensing server setting is read or emitted. The product ID is used internally to compute a SHA-256 identity digest; neither the ID nor digest appears in public evidence. Exactly one installed primary candidate is required. The bound query records retain numeric status/reason, nullable UTC Unix seconds for evaluation end and trusted time, grace minutes and observed guest UTC.

Known evaluation expiration fails before an activation request. Null or documented unset date values remain unknown, and status 5 or a grace-period error is not an expiration substitute. An already licensed product requires no activation request. Otherwise two fixed Microsoft-documented activation hosts receive parallel bounded DNS/TCP/TLS probes with normal certificate/hostname/revocation validation. Only endpoint IDs, booleans and numeric errors are retained. These probes send no HTTP payload and cannot prove that the licensing provider can activate or that it uses the same network/proxy path; their success is not an acceptance gate.

The supervisor starts at most one owned PowerShell process for ordinary activation. That process freshly reselects the unique primary product, compares its internal digest, rechecks expiration and current licensing state, and invokes the documented parameterless `Activate` method at most once. A now-licensed product skips the call; an expired, changed, ambiguous or unknown product stops. The process deadline is 100 seconds, with a 20-second query timeout and 60-second method timeout inside it. An observed return value, exception, process exit, or client termination does not invent a provider result. Missing replies remain null; a started method without an observed return fails with provider completion unverified. No retry, rearm, key installation, clock/expiry adjustment, licensing-service alteration, activation server override, policy change or trust change is made.

After an observed method response, up to two fresh 25-second licensing queries, separated by five seconds, must identify the same product and observe `LicenseStatus=1`. A zero method return alone can never satisfy this gate; a nonzero return is retained separately from a later genuinely observed Licensed status. No child account or harness starts while licensing is unverified. The newer `Get-OSLicenseInfo` cmdlet is not used.

It then copies the offline SDK into an owned Program Files directory, verifies copied bytes, compiles the independent harness, and runs its explicit alternate-account test. The harness creates its own nonadministrator B, verifies real distinct identities and both active sessions, requires its actual frame challenge, and only then attempts the one-point move/click/eight-character direct-input experiment. Existing identity, frame, input, parent-session and cleanup gates remain in effect. A COM success, login event, paint callback, started witness, or subprocess exit is insufficient.

COM1 is a file-backed QEMU serial endpoint. After reading and validating its per-run nonce, the supervisor writes a leading newline and `GUEST_HELLO_V1` carrying that nonce. The leading newline separates it from a possible unterminated firmware/boot line. Before this exact HELLO, the host discards at most 64 KiB of noise, retaining only a small possible HELLO-prefix suffix, within the existing 50-minute installation deadline. It reports byte counts and a fixed set of observed marker categories; no raw serial text or nonce is printed. Those marker labels do not identify an emitter or establish Windows boot. A wrong-nonce HELLO is an explicit failure. Before a valid HELLO, even a phase-shaped line is not accepted as a supervisor phase and does not stop the finite initial boot-key burst.

After HELLO, framing is strict: the supervisor emits at most 32 short phase beacons, at most 192 numeric activation records, and one UTF-8 JSON result no larger than 64 KiB with a byte length, SHA256, schema and the same per-run nonce binding. The complete serial stream is bounded to 2 MiB. The host rejects unexpected subsequent UART text, repeated HELLO, invalid activation ranges/order, bad digests/bindings and trailing data. HELLO or diagnostic records alone never yield a passing test. Only selected result fields are printed. Existing 30-second heartbeats now include whitelisted QMP state/running observations alongside numeric storage counters. Neither proves Windows progress or successful activation. Tool and QEMU failures print exit codes and fixed diagnostic categories, never raw stderr, command lines or paths.

### Activation progress and failure diagnosis

`GUEST_ACTIVATION_V1` has exactly six integers: iteration (the existing protocol accepts 1–18; this revision uses at most three queries), step, process exit/HRESULT code, candidate count, license status and unsigned reason code. Unavailable candidate/status/reason values are `-1`. The step values are:

| Step | Observation |
| --- | --- |
| 0 | Query operation entered, before process creation |
| 1 | Immediately before `Process.Start` |
| 2 | Owned process returned from creation |
| 3 | Both bounded output readers registered |
| 4 | Exit wait registered |
| 5 | Actual process exit observed |
| 6 | Query process and bounded output returned |
| 7 | Numeric candidate/status/reason payload parsed |
| 8 | Operation raised an exception; numeric HRESULT only |

The final `activation_audit` separately records before/after licensing snapshots, method process boundaries, optional native method reply, bounded connectivity and whether same-product Licensed status was actually observed. Its host projection rejects extra fields, unknown strings, unknown or ambiguous shapes, booleans disguised as integers, contradictory dates and unverified completion. No internal digest or raw CIM output is forwarded. The watchdog uses an immutable audit snapshot; it never serializes mutable result data from a second thread. Both stdout/stderr drains share the original process deadline. A failure to stop or reap any owned child, including the initial licensing query before a method process exists, has its own typed failure marker and sets `cleanup_unverified=true` in the common result handler.

These identify the last reached boundary, not the internal provider's state. No PowerShell/CIM stdout or stderr is forwarded. A dedicated OS thread starts its 240-second watchdog before the phase write and before any process creation. If expiry wins the atomic race against disarming, the experiment cannot continue to B or the harness. It attempts one nonce-bound failed result with `cleanup_unverified=true`, then terminates only its own supervisor process. Its own process-tree cleanup is not claimed on that hard path; host VM disposal remains separate. The terminal writer is claimed once, uses one native write with the existing five-second COM timeout, and does not wait indefinitely for the ordinary serial lock. The host independently limits the activation phase to 270 seconds, covering a suspended/stopped VM in which no guest thread can run.

On a failed outcome, before stopping the owned VM, the host makes one best-effort `query-status` and primary-display `screendump`. Only its private temporary image is passed to local Tesseract. A 16 MiB file cap, 4096-by-4096 dimension cap and exact binary PPM layout check occur before OCR; OCR is limited to ten seconds and 64 KiB TSV output. QMP has a five-second reply timeout. QMP's screenshot command has no file-size parameter, so the subsequent image cap bounds decoder input, not QEMU's file creation itself. Only high-confidence fixed Setup/OOBE/UEFI/activation/problem-message label IDs, dimensions, counters and success/failure booleans are emitted. Raw pixels, OCR words, arbitrary screen numbers, account names and paths are never published. The image is deleted in a `finally`, with the host's owned-directory cleanup as a further boundary. Missing labels or failed OCR mean unknown; they do not prove a live desktop, explain a hang, or change any acceptance gate. The host never resumes an unexpectedly paused guest to manufacture progress.

Success requires every actual guest prerequisite, the independent harness's different-account/frame/direct-input checks, the full harness cleanup flags, setup-medium removal, and verified host cleanup. `physical_input_isolation_verified` and `native_multiseat_verified` remain false even on a passing run. A kernel driver replacement, independent physical monitor/HID routing, compatibility with real GPUs/USB controllers, unattended lifecycle correctness and production performance remain outside this test's evidence.

## Deadlines, cleanup, and concrete unknowns

The job limit is 90 minutes. The orchestrator limits its own work to 80 minutes with a two-minute cleanup reserve; guest installation/testing is bounded to 50 minutes and the observed first-logon supervisor to 20 minutes. Desktop readiness has a three-minute bound, security query 90 seconds, the activation sequence allocates 195 seconds (25 query + 15 connectivity + 100 method process + 25/25 fresh queries + 5 delay), inside the dedicated 240-second watchdog and 270-second host phase limit, offline compilation five minutes, and the harness 225 seconds externally. Individual tool output and QMP operations are bounded. A finite initial 12-second space-key burst attempts to answer the stock boot-from-CD prompt. Run 40696191837 subsequently reached actual first logon, but that one observation does not guarantee prompt timing on another host. Failure to catch it remains failure, not a bootloader alteration.

On normal failure, timeout or handled termination, the orchestrator independently closes QMP, stops only the QEMU/swtpm processes it created, closes its files, and removes only its own temporary directory after both processes stop. Tool subprocesses have a separate owned process group so timeouts include apt/dpkg children. Failed cleanup is explicit and cannot produce success. An external hard kill or lost runner can prevent in-process cleanup reporting; absence of a cleanup report is not evidence of cleanup. The provider's eventual runner disposal is separate from an observed successful cleanup.

The inner harness verifies removal of its own B account/task/session/sandbox and restoration of its changed child-session feature state. `GuestWorkDirectoriesRemoved` refers to the owned copied source/runtime directories. It does not claim that Windows user profiles or system traces were erased by account deletion. Disposal of the entire owned guest disk removes A, profiles, setup state and all guest-local residue from this fixture's subsequent use. No reusable Windows image is exported.

Remaining runtime questions are the installed Evaluation expiration/time facts, the outcome of one ordinary activation request, and the existing child-session frame/input path. The cause of the earlier guest3 silence remains unknown. The prior run answered the initial boot, unattended first-logon, launcher, COM1, Secure Boot and TPM questions for that one configuration. Local source tests do not establish those observations for this revised source or another Windows/hardware configuration.

The answer file has been parsed for XML well-formedness, reviewed against the component documentation and processed by the actual Windows Setup run noted above. It has not been validated in Windows System Image Manager. Those are distinct checks from Python syntax and C# compilation.
